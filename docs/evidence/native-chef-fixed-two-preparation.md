# Optional fixed-two Chef transport: local preparation

Recorded 25 October 2026. The bounded Prep client now exposes
`fixedPayloadClient(client, maxPayloadBlocks = 1, inspect)` with accepted caps
one and two only. Existing `singleBlockClient(client, inspect)` retains its
original one-block behavior. The Docker wrapper reads private
`pins.maxPayloadBlocks`: absent or integer one preserves default one; integer
two is explicit opt-in; all other values fail before SDK/database/writer use.

Only outgoing request range/limit are clipped, using the minimum of original
limit, cap and range length. Canonical header range-one/limit-one requests stay
one. Fields, filters, options/AbortSignal and exact response objects are passed
through. PrepClient still owns its 32 MiB body limit/protocol checks; official
Chef 0.7.0 owns epoch/contiguous-page validation, scanner validation, per-block
commits and writer lifecycle. There is no adaptive scan, cursor rewrite,
response rewrite, automatic retry/fallback or manual checkpoint repair.

The existing `chef.config.ts`, schema, projection and generated bytes are
unchanged. Page size 16 and batch size one are unchanged. This is transport
coalescing, not batched commits or a changed Chef project identity. Operator
file/runtime pins and the image must change before use of the new code.

## Local verification

```powershell
npm --prefix indexers/zeer run typecheck
npm --prefix indexers/zeer test
node --test deploy/chef-docker/runtime.test.mjs
node --check deploy/chef-docker/runtime.mjs
node --check indexers/zeer/bounded-prep-client.mjs
git diff --check
```

Project typechecking and **12 indexer tests passed with zero skips**. The actual
npm-installed 0.7.0 CLI processes contiguous fixed-two pages, an odd final block
and a valid shorter partial page exactly once, without modifying config bytes.
Missing blocks, epoch conflicts and malformed continuation refuse publication;
AbortSignal interruption closes the fixture store without a commit. A provider
413 produces one failed two-block payload request, no one-block fallback and
no commit. Direct wrapper checks preserve original request/options/response
identity and canonical header bounds. The existing actual 205-note API test
also passes. Source/store/network/scanner behavior here uses local fixtures,
not a live namespace or native viewing key.

The Docker wrapper passes **26 tests with zero skips**, including default-one,
explicit-two and unsupported private-cap refusal. Existing source-only recovery
and external-network checks remain intact. Both syntax checks and diff checking
pass. No Docker, SSH, database connection, scanner invocation or live follower
change occurred during this preparation.

## Actual acceptance remains pending

Root must take a five-minute cap-one baseline with the builder idle and source
ingestion continuing, then use a reviewed new image/pins for a five-minute cap-two
candidate after positive stop/lock-release checks. Require at least **20% lower
fetch milliseconds per completed block** and **15% higher net catch-up rate**,
with no correctness/fatal/provider-413 or resource regression. Verify exact
canonical history/checkpoints, source freshness, single-writer ownership and the
unchanged paused financial baseline independently. No local timing or earlier
small read-only pair probe is treated as a passing actual comparison.

An unsuccessful comparison requires an explicit reviewed return to cap one;
the implementation must not choose fallback automatically. The candidate does
not authorize funds, renew financial authority or satisfy application readiness.
