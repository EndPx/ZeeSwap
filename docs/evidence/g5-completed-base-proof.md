# G5 completed Base receipt finality lag

Status: wired into G5 completed receipt verification and its physical boundary; validation so far is local isolated proof. No live operator, database, wallet or transaction action was performed by the implementation agent for this change. This does not establish a chain reorganization or complete a G5 acceptance gate.

`api/src/g5-completed-base-proof.ts` distinguishes a fresh Base finalized head below a previously confirmed original transaction from a missing or changed original transaction. It accepts only a completed order with its immutable confirmed originals. Forward orders require RESERVE and PAY; reverse orders require original FUND, COMMIT and SETTLE. It verifies the signed transaction bytes, signer, chain, destination contract, exact call and authorization, canonical receipt/block membership, event, recorded height/hash and operator fee before returning a typed observer WAIT. Missing, reverted, changed or unavailable originals remain hard failures. An IO exception resembling an observer WAIT cannot authorize this result.

The latest head must be fresh and coherent with the finalized head. Both canonical header hashes are reread. A reverse order also requires escrow state 6 at the latest head before WAIT; after finality catches up it requires state 6 at the finalized head. Reading an older finalized state during a proved lag cannot substitute for checking the current state. The lag floor includes the later confirmed operator SETTLE, rather than treating source FUND alone as completion evidence.

Operator RESERVE, PAY, COMMIT and SETTLE receipts must match persisted `actual_fee` exactly. The source payer FUND has no persisted historical actual fee in the deposit row. Its exact original signed raw/call/event/hash/height and canonical membership are checked, and its observed fee must remain within the original payer journal's prepared `maxCost`; this helper does not invent a historical FUND fee.

The physical-balance helper supplies a finalized head covering all recorded completed operator economic receipts before balances may be compared. At a regressed head it verifies all originals before yielding WAIT. Once the head covers the receipts, an actual balance deficit remains a hard error in the caller. Neither helper changes SQL, receipt confirmation, checkpoint freshness, controls, signing state or inventory.

`api/scripts/g5-completed-base-descriptor.ts` loads the protected production rows and decrypts their existing AAD contexts. It checks each confirmed transaction against its stored HMAC and maximum cost, and binds reverse funding to its original private approval, accepted escrow terms, correct Base signer WSL distribution, source deposit HMAC/AAD and exact output index. Fresh forward shielded source or reverse shielded delivery checks precede any Base WAIT in ordinary verification. The original `g5-operator.ts` catch returns `OBSERVER_WAIT` without setting completion flags or an incident; successful verification still follows its existing flag update path.
